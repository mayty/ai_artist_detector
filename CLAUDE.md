## Project Overview

Backend API for the **YTM AI Artist Detector** Chrome extension. The service determines whether YouTube/YouTube Music artists are AI-generated by querying multiple data sources (Soul Over AI, iimuzyka.top, explicit allow/block lists), matching against YouTube via `ytmusicapi` and YouTube Data API v3, and caching verdicts in SQLite.

## Key Commands

| Command | Description |
|---------|-------------|
| `make install` | Set up uv and install dependencies |
| `make check` | Run stylecheck + lintcheck + typecheck |
| `make style` | Format code with ruff |
| `make lint` | Auto-fix lint issues |
| `make typecheck` | Run pyrefly type checker |
| `make run_interactive` | Start API dev server on port 8080 |
| `make ingest` | Run full data ingestion pipeline |
| `make update_deps` | Update lock file and bump pyproject versions |
| `make db_shell` | Open interactive SQLite shell |

CLI entry point is `aiad` (Click-based): `aiad workers api-dev -p 8080`, `aiad ingest all`, `aiad db shell`.

## Development Setup

Uses **uv** for dependency management with Python 3.14. After `make install`, prefix commands with `uv run` (e.g., `uv run aiad workers api-dev`).

Production Docker image at `.docker/prod/Dockerfile` uses a multi-stage Alpine build. `docker-compose.yaml` brings up `api-prod`.

## Architecture

### Dependency Injection

Module-level singletons in `containers.py`: `core`, `repositories`, `external`, `services`. These are lazy-initialized via `@cached_property` and imported directly throughout the codebase — there is no DI framework. Adding a new service means adding it to the appropriate container class and wiring its dependencies.

### Layered Structure

```
ai_artist_detector/
├── cli/              # Click CLI subcommands (workers, ingest, db)
├── api/              # FastAPI routes (check artist, batch check, ping)
├── domain/           # Business logic
│   ├── verdict_controller.py  # Orchestrates data sources, reads SQLite cache
│   ├── youtube.py             # Artist matching against YouTube/YTM
│   └── data_source/           # Per-source services (soul_over_ai, iimuzyka_top, explicit)
├── external/         # HTTP clients (YouTube, YouTube Music, iimuzyka, Soul Over AI)
├── data/             # Persistence
│   └── sqlite/       # SQLite repos (mappings, overrides, search results, verdicts, metrics)
└── lib/              # Helpers (routing, TTL cache, rate limiting, logging, name matching)
```

### Routing

Routes are defined as nested dicts in `api/urls.py` and flattened by `construct_routes()` in `lib/helpers.py`. Add new endpoints by extending the nested dict structure.

### Data Sources

The `VerdictControllerService` aggregates AI verdicts from pluggable data sources. Sources are enabled/disabled via config (`enabled_sources` list). Each source service:
1. Fetches data from its external source
2. Matches artists against YouTube using `YouTubeAdapterService`
3. The controller collects all AI-confirmed artist IDs and stores them in SQLite

### Verdict Caching

SQLite stores the set of AI artist IDs. `VerdictControllerService.get_ai_artists()` caches in memory for up to 1 minute before re-reading from SQLite.

### Configuration

Pydantic settings loaded from YAML config files. Base config at `config/local.yaml`, with an override layer at `config/local.overrides.yaml` (gitignored). Config is accessed via `core.config`.

### Linting/Formatting

- **ruff** with `select = ["ALL"]` and a curated ignore list — single quotes, 120-char line length
- **pyrefly** for type checking
- Run `make check` before committing

## Workflow

- **Never hand a task back to the user unless `make check` passes.** Run `make check` yourself and fix any failures before considering the task done.
- When fixing check failures, try `make style` and `make lint` first. Resort to manual edits only if those tools cannot resolve the issue.

## API Endpoints

- `GET /ping` — health check
- `GET /youtube/v1/artists/check/{id}` — check if a single artist is AI
- `POST /youtube/v1/artists/check/batch` — batch check multiple artists
